> 项目：基于 LangGraph + Qwen2.5-VL-3B 的多模态 PPT 离线问答系统
> 测试环境：Docker Compose 生产镜像（FastAPI + Vue3/Nginx + PostgreSQL + Qdrant + Redis + Celery）

## BUG-001 引用卡片图片无法预览，接口返回 200 但图片空白

| 字段 | 内容 |
|---|---|
| 缺陷编号 | BUG-001 |
| 缺陷标题 | 引用卡片图片无法预览，接口返回 200 但图片空白 |
| 所属产品 | 多模态 PPT Agentic RAG 问答系统 |
| 所属模块 | 问答 → 引用溯源 |
| 缺陷类型 | 代码错误 |
| 严重程度 | 2（严重） |
| 优先级 | P1 |
| 影响版本 | v1.1.9 |
| 发现手段 | 用户报障 + 浏览器 DevTools 抓包复现 |
| 状态 | 已关闭（回归通过） |

**前置条件**：已上传含图片的 PPTX 文档并完成入库，进入会话页面。

**复现步骤**：
1. 上传含图表图片的 PPTX，等待入库任务完成；
2. 发起针对图片数值的问答（如"图 2 中某指标是多少"）；
3. 在回答下方的引用卡片中点击图片缩略图。

**预期结果**：引用卡片内图片正常展示，可点击放大查看原文图片。

**实际结果**：图片区域空白、加载失败。DevTools 显示 `GET /images/x.jpg` 状态码 **200**，但 Content-Type 为 **text/html**，`<img>` 解码失败。

**根因分析**：
- 后端 `_resolve_image_path()` 未将解析出的图片**绝对路径写回 `image.path`**，返回给前端的仍是相对路径；
- 前端请求 `/images/x.jpg` 未命中静态资源路由，落入 **SPA fallback**，404 被伪装成 200 + HTML —— 状态码完全不可信，导致问题定位被误导。

**修复方案**：
1. 后端新增 `ingest_tasks._public_image_path()`，在生成 caption **之前**写回绝对路径（顺序错误会导致图注静默丢失）；
2. 前端 `CitationCard.imageUrl` 增加三层路径兼容；
3. 编写存量数据回填脚本 `tools/fix_image_path.py`（幂等、默认 dry-run）。

**回归验证**：新入库文档与存量文档的引用图片均正常预览；以 `content-type` 与 `img.naturalWidth` 作为判定依据（不再信任状态码）。

**经验沉淀**：SPA fallback 会把 404 伪装成 200 —— 判断资源可用性必须看 content-type 或 `naturalWidth`，不能只看状态码。

## BUG-002 切换历史版本问答，返回的却是当前版本的数值

| 字段 | 内容 |
|---|---|
| 缺陷编号 | BUG-002 |
| 缺陷标题 | 切换历史版本问答，返回的却是当前版本的数值（版本过滤失效） |
| 所属产品 | 多模态 PPT Agentic RAG 问答系统 |
| 所属模块 | 检索 → 版本过滤 |
| 缺陷类型 | 逻辑错误 |
| 严重程度 | 1（致命，数据正确性问题） |
| 优先级 | P0 |
| 影响版本 | v1.1.9 |
| 发现手段 | 自建标注评测集（47 条三层评测）发现断言失败 |
| 状态 | 已关闭（回归通过） |

**前置条件**：同一文档已存在 v1、v2 两个版本，两版本中同名指标数值不同。

**复现步骤**：
1. 切换文档至 v1 历史版本；
2. 对 v1 版本独有数值发起问答（预期答案：412 / 87.6% / 11300）；
3. 核对回答中的数值与引用来源。

**预期结果**：答案与引用均来自 v1 版本内容。

**实际结果**：三条断言用例**全部返回 v2 版本数值**（468 / 89.2% / 12100），且无任何报错 —— 用户完全无感知地拿到了错误数据。

**根因分析**：`retrieval_service.build_filter` 中版本过滤条件存在 `OR is_active=true`，把"当前活跃版本"也保留进了候选池，使版本过滤实际退化为"扩召回"，历史版本问答时 rerank 后当前版本片段得分更高、被优先采纳。

**修复方案**：将 `version_override` 语义修正为"锁定版本"——过滤条件严格限定目标版本，移除 `OR` 分支。

**回归验证**：修复后跑回归金标准用例集（B10=3.20 / B11=41.5 / B12=520 / B13=1.28 / B14=3.56 / B05=1010）与组 A 数值断言（412 / 87.6% / 11300），全部通过；评测同时确认修复对 image_caption 路径同样生效。

**经验沉淀**：评测集的价值不仅在性能指标——**数据正确性缺陷（错误答案不报错）只有靠标注断言才能暴露**，功能冒烟发现不了。

## BUG-003 删除文档后，该文档的入库任务历史一并消失

| 字段 | 内容 |
|---|---|
| 缺陷编号 | BUG-003 |
| 缺陷标题 | 删除文档后任务历史被连带删除，无法追溯操作记录 |
| 所属产品 | 多模态 PPT Agentic RAG 问答系统 |
| 所属模块 | 文档管理 → 删除 |
| 缺陷类型 | 逻辑错误 |
| 严重程度 | 2（严重） |
| 优先级 | P1 |
| 影响版本 | v1.2.0 |
| 发现手段 | 用户报障 + 数据库比对复现 |
| 状态 | 已关闭（回归通过） |

**前置条件**：账号下已有若干文档，其中目标文档已完成入库、产生任务记录。

**复现步骤**：
1. 记录任务列表中该文档的任务条目；
2. 删除该文档（硬删除）；
3. 返回任务列表查看历史任务。

**预期结果**：文档被删除，但其历史任务记录保留可查。

**实际结果**：该文档相关任务记录**全部消失**。数据库核查发现两处连带删除：删除逻辑显式清理 `ingest_tasks`，且 `ingest_tasks.version_id` 外键为 `ON DELETE CASCADE`，随 `file_versions` 二次连带删除。

**根因分析**：删除链路存在**双重级联删除**，任务历史与文档生命周期被错误绑定。

**修复方案**：
1. 外键改为 `ON DELETE SET NULL`，删除文档时任务记录的 `version_id` 置空；
2. `ingest_tasks` 新增 `file_name` 快照列，删除文档时写入，保证列表仍能显示来源；
3. 已删文档的任务重试接口返回 400 拦截（`version_id is None`）；
4. 存量库执行 psql 迁移，`init/01_schema.sql` 同步更新，容器重建不退化。

**回归验证**：编写 `tools/testkit/verify_delete_keeps_tasks.py`（5 项断言）验证：任务保留、version_id 置空、快照写入、retry 拦截、文档三处（PG/Qdrant/磁盘）零残留，全部通过。

**经验沉淀**：删除类操作的验证必须覆盖"**删了该删的 + 留了该留的**"两面，且要落成可重复执行的断言脚本，而不是一次性人工检查。
